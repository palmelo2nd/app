## 1. 全体機能・開発方針

Webフロントエンド（`index.html` / `css/` / `js/`）と、GitHub Actions上で動くPythonバックエンド（`scripts/`）を組み合わせたハイブリッド構成のアプリ。フロントエンドはGitHub APIを直接叩いてワークフローを起動し、結果はデータリポジトリのファイル（CSV/JSON）として読み書きする。ローカルサーバーやDBは持たない。

### ファイル構成・命名規則

| ファイル | 役割 |
|---|---|
| `index.html` | エントリポイント。DOM構造のみ。JSロジックは書かない |
| `css/style.css` | UIデザイン・レイアウト定義 |
| `js/app.js` | 管制塔。イベント監視・DOM操作・各ページの制御に専念 |
| `js/modules/*.js` | 機能ロジック。1機能1ファイル |
| `scripts/*.py` | GitHub Actions上で実行するデータ取得・加工・検証スクリプト |

現在の`js/modules`構成：`storage.js`（トークンのLocalStorageキャッシュ）／`github.js`（GitHub API通信）／`csv.js`（CSVパース・書き出し）／`brokerCsv.js`（証券会社ネイティブCSVのパース。SBI・楽天の保有銘柄・実現損益）／`holdingsSummary.js`（保有銘柄の所有者別階層集計）／`defensiveScore.js`（[3.10 DEF](#310-defディフェンシブ度シミュレータ)のディフェンシブ度スコア算出）／`portfolioScore.js`（[4. スコア](#4-スコア)のポートフォリオスコア算出）。

modules配下の関数は4段落構成でexportする：(1) インポート → (2) インプット（引数でデータ・トークンを受け取る） → (3) メイン機能 → (4) アウトプット（`return`）。禁止事項：modules内でのDOM操作（`document.getElementById`等）、OWNER名・REPO名等の環境依存定数のハードコード（必ず引数として受け取る）。

### リポジトリ構成

コード（このアプリ本体・ワークフロー定義）とデータ（銘柄マスタ・株価CSV等）は別リポジトリで管理する。

| 種別 | リポジトリ | ブランチ | ローカルパス |
|---|---|---|---|
| コードリポジトリ | `palmelo2nd/app` | `main` | `app/brain/code/stock` |
| データリポジトリ | `palmelo2nd/app_data` | `main` | `app/brain/data/stock` |

### ページ構成

上部の表示切り替えボタンで4ページを切り替える（`js/app.js`の`STOCK_VIEWS`）。[3.8 ラベル](#38-ラベル)は高配当・優待の2ラベル（NG認定等は今後追加予定）を除き実装済み。全ページの実装状況は[0. もくじ](#0-もくじ)から各ページを参照。

2026-08-23：旧「銘柄提案」ページは、[4. スコア](#4-スコア)ページ内のモード切り替え（現状スコア／銘柄提案）に統合した。対象口座・スコア閾値パラメータが完全に同じ（同じポートフォリオ定義に対する「現状」と「1銘柄追加した場合」という表裏の関係）で、独立したページのままだとパラメータの二重入力になっていたため。

2026-08-24：旧「保有・履歴」ページ、旧「銘柄属性」ページ、旧「SIM」ページはいずれも、[3. データ更新](#3-データ更新)ページ内のモード切り替え（保有銘柄／売買履歴／株価／企業ID／配当／ラベル／銘柄情報／DEF）に統合した。データの登録・確認・更新という役割がいずれも「stockデータの手入力・取得」で共通しており、タブを分ける実益が薄かったため。あわせて旧「ダッシュボード」ページは表示名を「TOP」に変更した（内部の構造・機能に変更はなく、表示名のみの変更）。[4. スコア](#4-スコア)側の「現状スコア」「銘柄提案」モード切り替えも同日付でさらに廃止し、「銘柄提案」ボタン1つに一本化した（銘柄提案は現状ポートフォリオの計算を前提とする処理であり、ボタンを分ける実益が無かったため）。

## 2. TOP

ポートフォリオスコア・直近の提案などのサマリーを表示するトップページ（未実装）。現時点では[資産サマリー](#資産サマリー所有者別-総投資金額)のみ実装済み。アプリの初期表示タブ（クリック無しで表示される唯一のタブ）のため、他タブと異なりページ読込時点でトークンが入力済みなら自動集計される。

### 資産サマリー（所有者→口座区分→証券会社の階層集計）

`stock/holdings.csv`（[3.1 保有銘柄](#31-保有銘柄)で登録した内容）を**所有者→口座区分→証券会社**の順の階層で集計し、各階層の小計として**総投資金額**（保有銘柄それぞれの株数×取得単価の合計。取得原価ベースであり、現在の評価額・時価ではない点に注意）を表示する。集計ロジックは`js/modules/holdingsSummary.js`の`summarizeHoldingsHierarchy`。

- 表示順：所有者の行（総投資金額の降順、太字）→その配下に口座区分の行（同所有者内で降順、インデント）→さらに配下に証券会社の行（同口座区分内で降順、二段インデント）。各階層の金額はその配下の小計。
- 全所有者の行を並べ終えた末尾に、全体合計の「合計」行を表示する。
- **非表示チェックボックス**：既定でON（金額を隠した状態）。ONの間はすべての階層の金額欄が`●●●●●●`に置き換わり、所有者名・口座区分・証券会社名などラベルだけが見える状態になる（人前で画面を開いても金額が見えないようにするための機能）。チェックを外すと実際の金額が表示される。再取得は行わず、その場で表示を切り替えるのみ。
- 「読込」ボタンで`stock/holdings.csv`を再取得し、集計し直す。

## 3. データ更新

保有銘柄・売買履歴の登録から、株価データ（yfinance由来）の取得・鮮度確認・品質チェック、IRBANK企業ID（EID）の取得状況確認、配当情報の取得状況確認までをまとめたページ（タブ表示名は「データ」）。ページ上部の「保有銘柄」「売買履歴」「株価」「企業ID」「配当」ボタンで表示を切り替える（2026-08-24、旧「保有・履歴」ページと旧「データ更新」ページを統合し、5モードの切り替え型にまとめた）。保有銘柄・売買履歴の登録はブラウザ上の手入力・証券会社CSV取込、株価はGitHub Actions経由、IRBANK企業ID・配当情報の取得はいずれもローカル実行（[3.6](#36-irbank企業id取得)／[3.7](#37-配当情報取得)）。

### 3.1 保有銘柄

保有銘柄を「所有者×証券会社×口座区分×証券コード」単位の行として登録・編集・削除する。入力方法は「手動入力」「CSV入力」の2モードをタブで切り替える。

- **一覧**：`stock/holdings.csv`（データリポジトリ）の内容を表形式で表示（所有者／証券会社／口座区分／コード／銘柄名／株数／取得単価／最終更新日）。銘柄名は`stock/master.csv`から証券コードで解決して表示する（見つからない場合はコードをそのまま表示）。行クリックで下の入力フォームへ読み込む。「読込」ボタンで再読込できる。
- **最終更新日**（`updated_at`列。2026-08-23追加）：その行が最後に登録・更新された日時（JST）。手動入力の「新規」「適用」、CSV入力の取込のいずれでも、実行時点の日時が自動でセットされる（入力フォームに項目は無い）。追加より前に登録された行は空欄になる。
- **絞り込み**：所有者／証券会社／口座区分のプルダウン（現在登録済みの値から自動生成、既定は「すべて」）に加え、コード・銘柄名のフリーテキスト検索欄（2026-08-25追加）で一覧を絞り込める。表示のみに影響し、`holdingsRows`（保存対象データ）自体は変更しない。
- **並び替え**（2026-08-25追加）：一覧のヘッダー（所有者〜最終更新日）をクリックすると、その列で昇順／降順に並び替えられる（もう一度クリックで反転）。株数・取得単価は数値として比較する。
- **登録**：3.1.1・3.1.2いずれの操作も、この時点ではメモリ上の一覧（`holdingsRows`）を書き換えるのみでGitHubへは反映されない。ページ下部の「登録」ボタンを押した時点で、一覧全体を`stock/holdings.csv`へコミットする（brainアプリのオフライン対応とは異なり、現状はLocalStorageキャッシュを持たない。詳細は[`CLAUDE.md`](./CLAUDE.md)の「オフライン対応方針」を参照）。
- **未保存の変更が消えるリスクへの対策**（2026-08-25追加）：「登録」を押す前にページを閉じる・再読み込みすると、メモリ上の未保存の変更（`holdingsDirty`フラグで管理）が失われるため、その場合はブラウザの離脱確認ダイアログを表示する。
- **重複登録の防止**（2026-08-25追加）：「新規」を押した際、所有者×証券会社×口座区分×コードが完全一致する行が既に一覧にある場合は確認ダイアログを表示する（「適用」で更新すべきところを誤って「新規」で二重登録してしまうミスを想定）。
- **CSV出力**（2026-08-25追加）：「手動入力」「CSV入力」と並ぶ「CSV出力」ボタン（トグルではなく単発の書き出し操作）で、現在の`holdingsRows`全件（絞り込み前）を`stock/holdings.csv`と同じ列構成でファイルにダウンロードできる（手元控え・バックアップ用途）。
- 複数所有者（家族名義等）を区別して管理できるよう、「所有者」列を持つ（旧Jupyter実装の`02_OWNlist.csv`と同様のデータモデル）。

#### 3.1.1 手動入力

行単位で編集可能なテーブルUI（一覧クリック→フォームへ読込→新規/適用/削除）。

- **入力フォーム**：所有者・証券会社・口座区分は自由入力（登録済みの値をdatalistで補完）。証券コードを入力すると、`master.csv`から引ける銘柄名をその場でプレビュー表示する。
- **新規**：一覧での選択状態に関わらず、フォームの現在の内容を**新しい1件として追加**する。登録後はフォームがリセットされる。
- **適用**：一覧で選択中の行を、フォームの内容で**上書き更新**する（選択中の行が無い場合はエラー。新規追加は行わない）。
- **削除**：一覧で選択中の行を削除する（確認ダイアログあり）。

#### 3.1.2 CSV入力

証券会社の出力CSVファイルから保有銘柄をまとめて取り込む機能。証券会社（SBI証券／楽天証券）・所有者を選択し、ダウンロードしたCSVファイルを選択して取り込む。

- **対応状況**：SBI証券・楽天証券に対応（`js/modules/brokerCsv.js`の`parseSbiHoldingsCsv`／`parseRakutenHoldingsCsv`）。SMBC日興証券は保有銘柄が少数のため対象外とし、[3.1.1 手動入力](#311-手動入力)で運用する。
- **エンコーディング**：証券会社の出力CSVはPCからのダウンロード時はShift-JIS（cp932）だが、スマホからダウンロードした場合はUTF-8になることを確認した（2026-08-25、楽天証券アプリの資産残高CSVで実際に確認）。まずUTF-8として厳格デコード（`TextDecoder('utf-8', { fatal: true })`）を試し、失敗した場合のみShift-JISとして扱う自動判定にした（`decodeBrokerCsvBytes`）。
- **SBI証券のCSV構造**（「保有証券一覧」CSV）：「見出し（例: `株式（特定預り）`）→合計内訳→(空行)→同じ見出し（合計無し）→列ヘッダー→データ行」という空行区切りのブロックが繰り返される形式。パーサーはテキストを空行でブロックに分割し、末尾が「合計」の見出しブロック（内訳のみでデータを持たない）は無視、「銘柄コード」または「ファンド名」を列ヘッダーに持つブロックだけを処理する（旧Jupyter実装は行単位の状態機械で同じ見出しに複数回反応する無駄があったため、ブロック単位判定に整理し直した）。つみたて投資枠（投資信託）は保有口数を株数に変換（÷10000）。新NISAの成長投資枠／つみたて投資枠は区別せず、どちらも口座区分「NISA」として記録する。
- **楽天証券のCSV構造**（「資産残高（すべて）」CSVの「保有商品詳細」表）：SBIと異なり口座区分ごとのセクション分けが無く、1つの表（列ヘッダーに「銘柄コード・ティッカー」「口座」を含む）に全保有商品がまとまっている（口座は行ごとの列の値をそのまま使う）。パーサーはこの列ヘッダー行を探し、次の空行または次のセクション見出し（「■」で始まる行）までをデータ行として処理する。投資信託は銘柄コード欄が空のため銘柄名をコード代わりに使い、保有数量の単位（［単位］列）が「口」の場合は株数に変換する（÷10000）。旧Jupyter実装は「■◯◯口座」ごとのセクション分けを前提にしていたが、実際の出力形式（このCSV種別）はフラットな1表形式だったため、その前提ごと作り直した。
- **マージ方針**：取り込むと、選択した**所有者×証券会社に一致する既存行だけ**を今回の取込内容で置き換える。該当しない所有者・証券会社の行はそのまま保持される。
- **iPhone（Safari）でのダウンロード形式への備え**（2026-08-25）：証券会社によっては、iPhoneのSafariでダウンロードするとCSVではなく見た目だけ表形式のHTMLページが「〇〇.csv.html」という拡張子で保存される場合がある（保有銘柄のSBI証券CSVでは発生せず、[3.2 売買履歴](#32-売買履歴実現損益)のSBI証券CSVで確認された）。念のためこちらのファイル選択欄（`accept`属性）も`.csv`だけでなく`.html`等を選べるよう緩和し、読み込んだ内容がHTML形式と判定された場合は誤って文字化けしたデータとして取り込む前に案内を表示して中断するようにした（`looksLikeHtmlNotCsv`、実装は[3.2.2](#322-csv入力)と共通）。
- **バックアップ復元**（2026-08-25追加）：証券会社の選択肢に「バックアップ復元」を追加。[3.1のCSV出力](#31-保有銘柄)でダウンロードしたファイル（`stock/holdings.csv`と同じ列構成、UTF-8）をそのまま取り込める。証券会社CSVと異なりファイル自体が所有者・口座区分を列として持つ全件バックアップのため、部分マージではなく**一覧全体をファイルの内容で置き換える**（確認ダイアログあり）。この種別を選んだ場合、所有者欄は不要のため非表示になる。エンコーディングも証券会社CSV（Shift-JIS）と異なりUTF-8のまま読み込む。

### 3.2 売買履歴（実現損益）

過去実装（`past/(chk済)_C05_(R3)譲渡益の記録.ipynb`）を移植した、証券会社の実現損益記録機能。`stock/realized_gains.csv`（列：`id, owner, broker, asset_type, code, name, date, pnl`）に1取引1行の縦持ちの取引ログとして保存する。

- **保存方針の違い**：[3.1 保有銘柄](#31-保有銘柄)（`stock/holdings.csv`）は「現在の保有状況」を表す**洗い替え型**（登録のたびに一覧全体を置き換え）だが、こちらは過去の取引を積み上げていく**追記型**のデータのため、保存方式が異なる。「登録」を押した時点で、押した直前の最新の`stock/realized_gains.csv`を取得し直し、重複していない行だけを新規行として追記する（既存の履歴は書き換えない）。
- **重複判定（期間が重複するCSVの再取込み対策）**：証券会社・資産種別・コード・約定日・実現損益（`gainsBaseKey`）が完全一致するだけでは重複とみなさない。同日に同じ銘柄を複数回売買し、たまたま損益が同額になるケース（例：100株ずつ2回売買）があるため、**同じ基本キーの出現順（1件目・2件目…）まで含めて比較**する。具体的には、保存直前に取得し直した既存データ側でその基本キーが何件あるか（`existingCount`）を数え、仮登録一覧側で同じ基本キーが出現するたびに1件目・2件目…と数えていき、`existingCount`以下の出現分は「既存データ側に対応する取引がある＝重複」としてスキップし、それを超える出現分だけを新規追加する。これにより、「本当に複数ある同条件の取引」を保持しつつ、期間が重複するCSVを再取込みしても二重登録されない。
- **旧notebookとの違い**：旧notebook（`Data/jyouto/{年}.csv`という「年ごとのCSV・銘柄コードが列」の横持ち形式）は、同日同銘柄の取引をあらかじめ`groupby(["約定日","code"])["pnl"].sum()`で合算してから1マスに書き込み、既存値と完全一致すれば黙ってスキップする冪等性の仕組みだった（構造上1マスに1つの値しか持てないため、複数取引を区別して保持することはできなかった）。縦持ちの取引ログ形式に変更したことで、合算せずに1取引1行のまま記録しつつ、上記の出現順比較によって重複取込みへの安全性も両立できるようにした。
- **記録済み最新約定日**：「読込」を押すと、証券会社×資産種別ごと（[3.2.2](#322-csv入力)のCSV取込の区分と揃えている）に記録済みの約定日の最大値を一覧表示する（例：「SBI（国内株式）: 2026-08-11 まで記録済み」）。次に証券会社から実現損益CSVを取得する際、どの日付以降を対象にすればよいかの目安にする（[3.3 保存データの確認](#33-保存データの確認)の株価「更新最終日」と同じ考え方）。
- **一覧の絞り込み（2026-08-25）**：一覧テーブルの上に既定で閉じたExpander（詳細設定と同じ`<details>`）で「フィルタ」を用意しており、所有者／証券会社（実在する値から動的に生成する`<select>`。[3.1のフィルタ](#31-保有銘柄)と同じ考え方）・期間（開始／終了。約定日がその範囲内の行のみ表示。片側だけの入力も可）・銘柄（コード・銘柄名のいずれかに部分一致する自由入力の検索欄）で一覧を絞り込める。すべて表示のみに影響し、`realized_gains.csv`の内容や保存処理には影響しない。

#### 3.2.1 手動入力

所有者・証券会社・資産種別（国内株式／外国株式／投資信託）・証券コード・銘柄名・約定日・実現損益を入力し、「仮登録に追加」で下の仮登録一覧（未保存）に積む。

#### 3.2.2 CSV入力

証券会社の実現損益CSVから一括取込する。種類（SBI証券の国内株式／外国株式／投資信託、楽天証券）・所有者を選択し、ダウンロードしたCSVファイルを選択して取り込む。取り込んだ内容はいったん仮登録一覧に積まれるだけで、下部の「登録」ボタンを押すまでGitHubへは反映されない。

- **対応状況**：SBI証券（国内株式・外国株式・投資信託）・楽天証券（国内株式）に対応（`js/modules/brokerCsv.js`の`parseSbiDomesticRealizedGainsCsv`／`parseSbiForeignRealizedGainsCsv`／`parseSbiFundRealizedGainsCsv`／`parseRakutenRealizedGainsCsv`）。
- **エンコーディング**：[3.1.2](#312-csv入力)と同様、UTF-8を優先しつつ失敗時のみShift-JISとして扱う自動判定（`decodeBrokerCsvBytes`、2026-08-25変更）でデコードしてから解析する。
- **SBI証券のCSV構造**：先頭2列が「約定日」「口座」の行をテーブルヘッダーとして検出し、以降を取引データ行として読む（国内株式・外国株式・投資信託で共通）。国内株式・外国株式は「銘柄名」または「銘柄名/ティッカー」列が「会社名＋コード（またはティッカー）」の連結になっているため、末尾の英数字トークンをコード側として分離する（国内株式は3〜5桁に限定した上で数字のみなら4桁ゼロ埋め、外国株式は桁数を限定せず大文字化のみ）。投資信託は「ファンド名」をコード・銘柄名の両方にそのまま使う。
- **楽天証券のCSV構造**：SBIと異なりブロック構造を持たない単純な1表形式（1行目が列ヘッダー）。「銘柄コード」列をそのままコードとして使う（4桁ゼロ埋め）。銘柄名の列は無いため、一覧表示時は`stock/master.csv`から証券コードで名前を解決する（[3.1](#31-保有銘柄)の一覧と同じ仕組み）。
- **仮登録一覧**：手動入力・CSV取込どちらの内容も同じ仮登録一覧（未保存）にまとまる。行ごとに「削除」で個別に取り消せる。
- **バックアップ復元**（2026-08-25追加）：種類の選択肢に「バックアップ復元」を追加。[3.2のCSV出力](#32-売買履歴実現損益)でダウンロードしたファイル（`stock/realized_gains.csv`と同じ列構成、UTF-8）をそのまま仮登録一覧に積み込める。[3.1.2](#312-csv入力)のバックアップ復元と異なり、売買履歴は追記型データのため一覧全体を置き換えるのではなく仮登録一覧に加えるだけにとどめ、既存の履歴との重複判定は通常のCSV取込と同じく「登録」ボタン押下時（3.2の重複判定）に委ねる。この種別を選んだ場合、所有者欄は不要のため非表示になる（ファイル自体が所有者列を持つため）。取り込み時にファイル固有の`id`列は破棄し、「登録」時に新しいIDを振り直す。
- **CSV出力**（2026-08-25追加）：「手動入力」「CSV入力」と並ぶ「CSV出力」ボタン（トグルではなく単発の書き出し操作）で、「読込」済みの`realizedGainsRows`全件（仮登録中の未保存分は含まない）を`stock/realized_gains.csv`と同じ列構成でファイルにダウンロードできる（手元控え・バックアップ用途）。
- **未保存の変更が消えるリスクへの対策**（2026-08-25追加）：[3.1 保有銘柄](#31-保有銘柄)と同様、仮登録一覧（`gainsPendingRows`）に未保存の内容が残ったまま離脱しようとすると、ブラウザの離脱確認ダイアログを表示する。
- **iPhone（Safari）でのダウンロード形式への対応（一部）**（2026-08-25）：SBI証券をiPhoneのSafariでダウンロードすると、CSVではなく見た目だけ表形式のHTMLページが「〇〇.csv.html」という拡張子で保存される場合がある（実際にSBIの売買履歴CSVで確認済み）。ファイル選択欄（`accept`属性）を`.csv`だけでなく`.html`等も選べるよう緩和し、実際に読み込んだ内容がHTML形式と判定された場合は、誤って文字化けしたデータとして取り込む前に「HTML形式のようです（未対応）」という案内を表示して処理を中断するようにした（[3.1.2](#312-csv入力)と共通の`looksLikeHtmlNotCsv`）。HTML形式のファイル自体からのデータ抽出（`<table>`の解析）は未対応のまま（[6. 使い勝手改善タスクリスト](#6-使い勝手改善タスクリスト)参照）。

#### 3.2.3 銘柄別 実現損益合計

「読込」済みの`stock/realized_gains.csv`全体（仮登録中の未保存分は含まない）を証券コードごとに合計し、横棒グラフで表示する。既定で閉じた開閉式パネル（詳細設定と同じ`<details>`）にまとめており、普段は一覧の確認をメインにしつつ、必要な時だけ開いて確認する運用を想定している。旧notebook同様、プラス（利益）・マイナス（損失）を別々のグラフに分け、それぞれのグラフ内の最大値（絶対値）を基準にバーを0から伸ばす（プラス・マイナスでスケールは共有しない。外部グラフライブラリは使わず、[3.10 DEF](#310-defディフェンシブ度シミュレータ)のヒストグラムと同じdiv要素による自前実装）。各グラフの見出しには、そのグラフに含まれる銘柄の合計金額（プラス側・マイナス側それぞれの総和）を表示する。
- **集計期間の絞り込み（2026-08-25）**：グラフの上に「期間（開始）」「期間（終了）」の日付入力欄があり、約定日（`date`列）がその範囲内の行だけを対象に再集計する。空欄のままの側は無制限（開始のみ入力＝それ以降すべて、終了のみ入力＝それ以前すべて）。値を変更するたびに通信なしで即座に再描画する（読込済みの`realizedGainsRows`をその場でフィルタするだけのため）。

### 3.3 保存データの確認

- 「チェック」ボタンで、鮮度チェック（`check-price-freshness.yml`）とデータ品質チェック（`validate-stock-prices.yml`）を同時に起動し、完了を待って結果を表示する（行単位の詳細チェックはここでまとめて行い、常時表示はサマリーのみ）。どちらも`stock/delisted.csv`（後述）に登録済みの銘柄を対象から除外する。
- **常時表示サマリー**：チェック日時（JST表示。`freshness_report.json`の`checked_at`はUTCで保存されているため+9時間して整形）／対象件数、全体の最新日付／最古日付、日付問題（既定10日超過）件数、品質問題件数、上場廃止（除外）件数をまとめて表示する。日付問題・品質問題が1件以上ある場合は赤字で強調する。
- **詳細（2列、いずれもExpander閉が既定）**：どちらの列も、日付／問題内容ごとの内訳の1つ上の階層に「内国株式」「その他（ETF等）」の分類（`master.csv`の`asset_type`で判定。ETF・ETNや`master.csv`に無いコード〈N225等〉は「その他」扱い）を挟んで表示する（2026-08-18追加。yfinanceはETF側で更新漏れ・欠損が起きやすく、内国株式と混在させると個別株側の問題が埋もれるため区別できるようにした）。該当が0件の分類は表示されない。「まとめて再取得」系のボタンは従来通り分類をまたいだ全件対象のまま変更していない。
  - 1列目「更新最終日」：`freshness_report.json`の日付ごとの銘柄数分布（展開すると該当銘柄コード一覧を表示）。該当銘柄コードが分かる行には「再取得」ボタンを添え、その日付グループだけを`fetch-stock-prices-by-codes.yml`（`mode=update`＝差分更新のみ。全期間の取り直しではない）で再取得できる。完了後は自動的に本チェックを再実行し、直ったかどうかを反映する。
    - **まとめて再取得**：分布の下に「最新日付のグループも含める」チェックボックスと「まとめて再取得」ボタンがあり、複数の日付グループを一括で再取得できる。既定（チェックOFF）では全体の最新日付（`report.latest_date`）のグループを対象から除く。同日中に実行する場合、既に最新日付まで届いている銘柄は当日分がそもそも保存されない（[CLAUDE.md](./CLAUDE.md)参照）ため再取得しても無駄になるからである。一方、最新日付自体が数日前で止まっている状況（bulk更新が完走していない等）では、チェックをONにして最新日付のグループも含めた全体を対象にできる。
    - この下に、登録済み上場廃止銘柄・登録済み追加対象銘柄の一覧（それぞれサブExpander・デフォルト閉。削除ボタンで登録取り消し可）も表示する。
  - 2列目「データ品質」：`validation_report.json`の問題を種類・内容ごとにグルーピングして件数付きで一覧化（展開すると該当銘柄コード一覧を表示）。問題が無ければ内訳無し。各グループには「再取得」ボタンがあり、該当銘柄をまとめて`fetch-stock-prices-by-codes.yml`（`mode=full`）で取得し直せる。更新最終日側の「再取得」（`mode=update`）と違い、データ品質の問題は既存データの途中にあることが多く差分取得では直せないため`mode=full`にしているが、無条件に2013年以降の全期間を取り直すと無駄が大きいため、**問題箇所の日付が分かるグループ（終値欠損・重複日付・N225取引日との突き合わせ欠損）は、その日付の最小〜最大（前後3日バッファ）だけをピンポイントで再取得する**（`--start-date`/`--end-date`指定）。日付を持たない問題（並び順異常等）は従来通り全期間を取り直す。一覧の下には「まとめて再取得」ボタンもあり、全グループを横断した該当銘柄（重複除去済み）を全期間`mode=full`でまとめて再取得できる（こちらはピンポイント化していない）。完了後は自動的に本チェックを再実行し、直ったかどうかを反映する。チェック項目・欠損検出の考え方は[CLAUDE.md](./CLAUDE.md)を参照（2026-08-17に、日数閾値による推測からN225取引日カレンダーとの突き合わせ方式へ変更し、「最終更新日が古い」チェックは[3.3](#33-保存データの確認)「更新最終日」側と重複するため除外、上場廃止登録銘柄も除外対象に追加した）。
- **上場廃止銘柄の登録**：証券コード（カンマ区切りで複数可）を入力して「登録」を押すと、`stock/delisted.csv`（列：`code, note, updated_at`）へ即座にコミットされる。登録済みの銘柄は以降の株価取得（[3.4](#34-株価の更新最新株価取得)／[3.5.2](#352-株価一括取得銘柄マスタから範囲指定)）・鮮度チェックの対象から除外される。yfinanceの取得失敗を根拠にした自動判定はせず、必ず人が確認して登録する方式にしている（誤検知を避けるため。[添付6](#添付6-保留事項今後の検討課題)参照）。先に「チェック」を1回実行してから登録する必要がある（既存データを取りこぼして上書きするのを防ぐため）。
- **追加対象銘柄の登録**：`master.csv`には無いが継続的に差分更新したい銘柄（N225等の指数、`master.csv`にまだ反映されていない新規上場銘柄など）を、証券コード（カンマ区切りで複数可）を入力して「登録」を押すと`stock/extra_targets.csv`（列：`code, yf_ticker, note, updated_at`）へ即座にコミットする（操作感は上場廃止銘柄の登録と同じ）。登録した銘柄は、[3.4](#34-株価の更新最新株価取得)の一括更新が`offset=0`から実行される際に`master.csv`由来の対象へ合流させて継続的に差分更新される。`yf_ticker`列は通常空欄でよい（東証銘柄は自動で`{code}.T`に変換される。N225のような特殊ティッカーはコード側に既定値があるため、アプリからの登録では指定不要）。`master.csv`側に後日反映されて重複登録になっても、対象リストの合流時に重複除去するため実害は無い。

### 3.4 株価の更新（最新株価取得）

日常運用で使うボタン1つ。押下すると銘柄マスタ（`master.csv`）から対象銘柄（`status=listed`かつ`asset_type`が「内国株式」または「ETF・ETN」）の件数を数え、一括取得ワークフロー（`fetch-stock-prices-bulk.yml`）を`offset=0`・`mode=update`（差分更新）で起動する。

- 進捗バー：20件処理するごとに自動コミットされる仕組みを利用し、直近のコミットメッセージから処理済み件数を読み取って表示する。
- 前回実行がまだ進行中の場合は、同時実行によるデータリポジトリへのコミット競合の恐れがある旨を警告し、続行確認を挟む。
- ブラウザを閉じてもワークフロー自体はGitHub側で継続する（再度開いて「チェック」を押せば結果を確認できる）。
- **取引時間中に実行しても、当日分は保存しない**（2026-08-17判断）：`fetch_prices.py`はyfinanceから返る当日分の終値を「取引時間中の途中価格」とみなし、常に除外して保存する（前営業日以前の確定値のみ保存）。日中に何度実行しても当日は次回以降の実行で再取得対象になり続け、確定後の値で自然に埋まる。詳細は[CLAUDE.md](./CLAUDE.md)を参照。

### 3.5 詳細設定（株価取得）

日常運用では使わない操作をまとめた折りたたみセクション。

#### 3.5.1 株価取得（銘柄コードを直接指定）

証券コード（カンマ区切りで複数指定可）と取得期間（空欄なら2013年以降の全期間）を指定し、単体取得ワークフロー（`fetch-stock-prices.yml`）を起動する。新規上場銘柄の初回取得など、個別に確認したい場合に使う。

- **日経平均株価（N225）**：証券コード欄に`N225`と指定すると、日経平均（yfinanceティッカー`^N225`）を他の銘柄と同じ形式（`stock/prices/N225.csv`、列: date, close）で取得・保存できる（`fetch_prices.py`の`INDEX_TICKERS`で特例扱い）。将来のディフェンシブ判定・ポートフォリオスコアでベンチマーク比較に使う想定。銘柄マスタ（`master.csv`）には存在しない特殊ティッカーだが、2026-08-17以降は[3.4](#34-株価の更新最新株価取得)の一括更新（`offset=0`で始まる実行の先頭サブバッチ）にも自動的に含まれるようにした（`fetch_prices.py`が`--master`モードの`offset=0`実行時にのみ`N225`を追加する。サブバッチが進んでも重複取得はしない）。個別に更新したい場合や、`offset>0`から始まる範囲取得では引き続きこのフォームを使う。

#### 3.5.2 株価一括取得（銘柄マスタから範囲指定）

銘柄マスタ全体を対象に、開始位置（offset）と件数（limit）、モード（`initial`＝未取得銘柄向け全期間取得／`update`＝差分更新）を指定して`fetch-stock-prices-bulk.yml`を起動する。新規上場銘柄の初回取得など、範囲を区切って処理したい場合に使う（日常の差分更新は[3.4](#34-株価の更新最新株価取得)で足りる）。

### 3.10 DEF（ディフェンシブ度シミュレータ）

過去実装（`past/(chk済)_C02-2_ディフェンシブ判定ラベル付け.ipynb`）のスコアリングロジックを移植した試算ツール（`js/modules/defensiveScore.js`）。銘柄の株価を日経平均（N225）と比較し、下方β（downside beta。下落局面に絞った相関×ボラ比）からディフェンシブ度スコア（0〜100、高いほど景気非連動）を算出する。旧実装の手動教師ラベル（`L_def`）は廃止し、連続スコアによる評価に一本化した。ディフェンシブ／オフェンシブという二値判定・判定しきい値の概念自体を持たず（2026-08-22廃止）、スコアの連続値でのみ評価する。2026-08-24、旧「SIM」タブから「データ更新」タブのDEFモードへ移動した（機能・計算ロジックに変更はない）。

- **2026-08-22の設計変更（背景）**：本アプリの用途は、保有銘柄の購入金額でスコアを加重平均し、ポートフォリオ全体のディフェンシブ度を算出すること（銘柄提案での目標値判定に使う想定）。この用途には、加重平均が数学的に厳密に合成できる指標（β_portfolio = Σ 購入金額比率 × β_i）が必要で、これに合致するのはβのみ。従来の「下落局面相関・ボラ比・最大下落比の3指標をそれぞれ重み付けして加重平均する」方式は、相関・ボラ比・最大下落比のいずれも加重平均では正しく合成できない（特に最大下落比は分散効果を無視することになり、加重平均すると実態より悲観的な値になる）ため、下落局面相関とボラ比を統合した単一のβに一本化した。最大下落比（MDD比）はこの整合性の問題から完全に廃止し、参考情報としても保持していない。「改善①〜④」（旧notebookのMDDクリップ・vol許容レンジ緩和・条件付き重み変更・救済ルール）はいずれも対象外（MDDクリップ・救済ルール・条件付き重み変更はMDD比廃止と単一指標化により不要、vol許容レンジ緩和相当は下記「指標の定義」のgood/bad閾値で代替）。あわせて、ディフェンシブ／オフェンシブの二値判定・判定しきい値の概念も廃止した（銘柄選定はスコアの連続値のみで行う方針としたため）。
- **対象銘柄・期間**：証券コード（カンマ区切りで複数可）を指定するか、空欄なら`stock/labels.csv`の高配当銘柄（`L_高配当=1`）を対象にする。期間は暦年（1〜12月）区切りで、N225の最終データ日が属する年を除いた過去N年分（銘柄側もN225と同じ年範囲で揃えて計算する）。
- **βのgood/bad閾値（詳細設定）**：βがgood以下なら100点、bad以上なら0点、間は線形補間（既定good=0／bad=2。β=1〈市場平均並みの感応度〉でちょうど50点になるよう対称に設定している）。2026-08-22の実測（対象：高配当銘柄、約120銘柄）ではβの分布が概ね-0.08〜1.54だった。旧既定値（good=0.5／bad=1.5）だと分布下限側の銘柄の15%程度が100点にクランプされ差が付かなくなるため、good=0／bad=2に拡げた（0〜2という区切りの良い数値を優先）。
- **指標の定義（詳細設定）**：βの算出方法そのものに関わるパラメータ（`js/modules/defensiveScore.js`の`calcDefensiveScore`に渡り、計算に反映される）。
  - **下落局面の閾値**（既定0）：N225の期間リターンがこの値未満の期間を「下落局面」とみなす。βの相関・ボラ比の両方をこの下落局面だけに絞って算出する。
  - **リターン算出期間（週）**（既定2週、1〜8週。4週が月次相当）：βの算出に使う期間リターンを、暦月の代わりに何週間ごとで切り出すかを指定する。銘柄・N225の両方に同じ起点（対象期間の開始年の1/1）で区切りを揃える。データ十分性の判定（重複期間・下落局面期間がそれぞれ最低限必要な件数以上あるか）も、暦月換算で従来と同じ基準（重複期間2年分・下落局面1年分相当）になるようこの設定に応じて自動的にスケールする。
  - **外れ値クリップ**（既定0.5）：期間リターンの絶対値がこの値を超えたら丸めてからボラ比（標準偏差比）を計算する（銘柄・N225の両方に同じ値を対称適用。相関の算出には適用しない）。
- **計算**：「計算」ボタンで対象銘柄の株価CSV（`stock/prices/{code}.csv`）とN225を取得し、6件ずつのバッチで並列にスコアを算出する。結果はメモリ上（`simResults`）に保持するのみで、この時点ではどこにも保存されない（あくまで試算用。保存は下記「適用」で行う）。
- **指標分布（ヒストグラム）**：プルダウンでスコア／β／下落局面相関／下落局面ボラ比のいずれかを選んで分布を表示する。各binの棒は、旧実装の手動ラベル（`REFERENCE_LABELS`。past由来の参考データで、保存先を持たない比較表示専用）による「旧ディフェンシブ／旧オフェンシブ／参考ラベル無し」の3区分の積み上げグラフで表示する。
- **銘柄一覧（結果テーブル）**：列はコード・銘柄名・スコア・β・下落局面相関・下落局面ボラ比のみ（判定・旧参考ラベル・対象期間数の列は持たない）。列ヘッダークリックでその列を基準に昇順・降順ソートできる（同じ列の再クリックでトグル、別の列へ切り替えると降順から開始。既定はスコア降順）。
- **適用（銘柄選定用スコアとして保存）**：一覧下部の「適用」ボタンを押すと、スコアが算出できた銘柄（データ不足・取得エラーは対象外）のディフェンシブ度スコアを`stock/scores.csv`（列：`code, defensive_score, updated_at`）へ保存する。マージ方式（対象コードだけ更新・追加し、対象外の銘柄の既存スコアはそのまま残す。全件洗い替えはしない）。DEFモードは`scores.csv`を読み込んでキャッシュするステップ（読込ボタン）を持たないため、押下のたびにGitHubから最新の内容を取得してからマージする。

### 4.3 スコア履歴

2026-08-29追加。[4.1 現状スコア](#41-現状スコア)の【全体】ブロックの直後にのみ表示する（所有者別ブロックには表示しない。組み合わせ爆発を避けるため）。

- **スコアを記録**：ボタンを押すと、直前に計算した【全体】のスコア1行（投資金額(補)・年間配当・目標配当達成率・配点予算・各下位指標の得点と達成比率など）を、`stock/score_history.csv`（列：`id, recorded_at, note, total_invest_adj, total_dividend, achievement_rate, budget_growth, budget_risk, score_yield, score_achievement, score_industry, score_stock, score_defensive, score_growth_total, score_risk_total, score_total, yield_ratio, industry_ratio, stock_ratio, defensive_ratio`）へ追記する。積み上げるデータのため洗い替えはせず単純追記のみ（重複判定も無い。押すたびに必ず1行増える）。`note`列にはその時点の対象口座選択（所有者／証券会社／口座区分）を短い説明文で記録する（後から履歴を絞り込む用途ではなく、参考表示のみ）。計算のたびに自動保存はされない。
- **履歴を読込**：`stock/score_history.csv`を取得し、直近10件をチェックボックス一覧（日付＋スコア合計）で表示する。チェックを付けると、その記録をレーダーチャートに比較表示できる（最大3件まで。それ以上は選べない旨のアラートを出す）。
- **レーダーチャート（5指標の達成比率）**：実質利回り・達成率・業種分散・DEF・銘柄集中の5軸を、いずれも「達成比率×100（0〜100%）」で正規化して表示する。**得点そのもの（配点予算×達成比率）ではなく比率を使う理由**：達成率に応じて配点予算自体が変動するため、生の得点だけで時系列比較すると「配点予算が変わっただけ」で見た目が動いてしまい、実力比較として不公正になるため。現在値（実線）に、選択した過去スナップショット（破線、最大3件）を重ねて描画する。
- **時系列推移（2軸折れ線グラフ）**：`stock/score_history.csv`の全記録を日付順に並べ、推進系合計（`score_growth_total`）・防衛系合計（`score_risk_total`）の推移を2本の折れ線で表示する（対象口座の絞り込みはせず、記録した全スナップショットをそのまま並べる）。
- **描画方式**：本アプリは外部グラフライブラリを使わずSVGを自前実装する方針（[3.10 DEF](#310-defディフェンシブ度シミュレータ)のヒストグラムや[4.1](#41-現状スコア)の横棒グラフは従来div実装だったが、五角形・折れ線は形状上SVGが自然なため、本アプリで初めてSVGを採用した）。座標計算は`js/modules/chartGeometry.js`（DOM操作を持たない純粋関数のみ）に分離し、`<svg>`要素の組み立ては`js/app.js`側で行う。

## 添付1. 共通機能（全ページ共通）

### 常時表示バー（PW入力欄）

全ページ上部に固定表示される、GitHub Personal Access Token（PAT）の入力欄（ラベル表記は「PW」）。GitHub連携が必要な各ページで共通して使う。

コードリポジトリ（`app`）・データリポジトリ（`app_data`）の両方に対して、Actions・Contentsをread/writeできる単一のトークンを入力する（ワークフロー起動`dispatchWorkflow`、ファイル読み書き`fetchFile`／`commitFile`等すべてに共通で使う）。入力欄右の「保存」ボタンを押すとLocalStorageへ保存され（キー：`stock_token`）、次回以降は入力済みの状態で開く（一度保存すれば十分なため、入力するたびに自動保存する方式ではない）。旧・ID/PW2欄だった頃の保存値（`stock_id_token`／`stock_pw_token`）や、さらに古い単一PAT欄時代の保存値（`stock_pat_token`）が残っている場合は、そちらから引き継がれる。

> 以前はリポジトリごとに「ID」「PW」の2欄に分けていた（最小権限の原則を意図したもの）が、実運用では1つのトークンに両リポジトリの権限をまとめて付与する運用になったため統合した（[添付5. トークン運用の変更履歴](#添付5-トークン運用の変更履歴)参照）。

### 表示切り替え（タブ）

TOP／データ／スコア／Infoの4ページを切り替える（データページ内に「保有銘柄」「売買履歴」「株価」「企業ID」「配当」「ラベル」「銘柄情報」「DEF」の8モードを持つ。スコアページは2026-08-24にモード切り替えを廃止し、「銘柄提案」ボタン1つで現状スコア・銘柄提案の両方を出力する単一ページになった）。データタブを開いたとき、トークンが入力済みなら現在アクティブなモード（既定は「保有銘柄」）に対応する一覧・パネルを自動的に読み込む（保有銘柄／売買履歴モードなら[3.1 保有銘柄](#31-保有銘柄)・[3.2 売買履歴](#32-売買履歴実現損益)の一覧、株価モードなら[3.3 保存データの確認](#33-保存データの確認)のパネル、企業IDモードなら[3.6](#36-irbank企業id取得)、配当モードなら[3.7](#37-配当情報取得)、ラベルモードなら[3.8](#38-ラベル)、銘柄情報モードなら[3.9](#39-銘柄情報)の状態。DEFモードは「計算」を押すまで何も取得しない試算専用のため自動読み込みの対象外）。スコアタブを開いたとき、トークンが入力済みなら対象口座チェックボックス（[4. スコア](#4-スコア)参照）を保有銘柄一覧から構築する。Infoタブを開いたとき、トークンが入力済みなら[5. ## 添付6. 保留事項・今後の検討課題

過去のノートブック実装（`past/`）との突き合わせで判断を保留した項目。関連する実装に着手する前に、まずここを確認する。

- **上場廃止判定**（C04_2由来。2026-08-11判断、2026-08-17に一部対応）：yfinanceでの取得失敗を根拠に**自動**で上場廃止と判定する旧実装には誤検知のリスクがあった（一時的な取得失敗を廃止と誤判定しうる）。2026-08-17、[3.3](#33-保存データの確認)に**人が確認して手動登録する**方式（`stock/delisted.csv`）を実装した。自動判定ではなく人間の確認が根拠になるため、この誤検知リスクを回避できている。自動判定については引き続き未着手（着手時は以下から検討する）：
  - 取得失敗の原因を区別する（ネットワーク等の一時的エラーと、データが存在しない失敗を分けて扱う）
  - 1回の失敗では判定せず、複数回（例: 連続5〜10日分の更新）失敗が続いた場合のみ疑いありとする
  - **本命案**：yfinanceの取得失敗ではなく、`master.csv`の再生成（JPX公式データ由来）でコードが消えたことを上場廃止の根拠にする。JPXの上場銘柄一覧という確定的なソースに基づくため、yfinance側の取得不安定さに左右されない、より信頼できる判定方法になる。実装する場合も、手動登録（`stock/delisted.csv`）と共存させる（自動判定の結果を追記していく形にする）想定。
- **バッチ一括取得・active-onlyウォームアップ**（C04_2由来。2026-08-11判断）：数千銘柄の初回バックフィルを高速化する仕組み（yfinanceへの複数ティッカー一括リクエスト＋失敗時の分割retry）。現状の「1銘柄ずつ順次取得＋20件ごとに自動コミット」で運用上問題ないため、当面は改善しない。
- **REIT/PRO Marketの取得対象拡大**（C04_2由来。2026-08-11判断）：バルク取得（[3.4](#34-株価の更新最新株価取得)）の既定対象（`内国株式`・`ETF・ETN`）にREIT等を含めるかどうか。IRBANK（[C01](#添付4-過去資産レガシー実装)）で銘柄の基本情報を取得できるかに依存するため、その実装状況を見てから判断する。現状は[3.5.1](#351-株価取得銘柄コードを直接指定)の個別コード指定で取得可能。
- **`L_所有`ラベルの自動反映**（C03由来。2026-08-11判断）：保有銘柄登録時に銘柄マスタ側へ「保有中」フラグを自動で立てる旧機能。使わない見込みのため保留。[3.8 ラベル](#38-ラベル)の設計時に要否を再検討する。
