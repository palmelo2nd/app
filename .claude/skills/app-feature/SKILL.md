# アプリの新機能の進め方

## 使う場面
- 使う：新しい画面・タブを作る、app_dataの列（データ構造）を増やす・変える、複数のファイルにまたがる変更
- 使わない：文言・見た目の調整、1ファイルで済む不具合の修正（今までどおりプランモードで進める）
- 迷ったら「この手順で進めますか」とユーザーに一言聞く

## 置き場所
- `C:/Users/fuji1/Desktop/app/app_data/docs/<アプリ>/<yymmdd>_<機能名>.md`（非公開のapp_data側。コードのリポジトリ`app`は公開なので置かない）
- 1機能＝1ファイル。下の「ファイルの型」の3節（要件定義・設計・タスク）を1つのファイルに書く

## 手順
1. **要件定義**：ファイルを作り、「要件定義」の節を書く。ユーザーに確認し、未決事項を決めてもらう（質問は1回3個まで）
2. **設計**：「設計」の節を書く。対象アプリのCLAUDE.mdと`app/CLAUDE.md`の共通ルール（コード/データ分離、オフラインファースト、キャッシュバスティング、UI/UX設計方針）に沿っているかを確かめる
3. **タスク**：「タスク」の節にフェーズ分けしたチェックボックスを並べ、**ここでユーザーの承認を得る**。承認前に実装しない
4. **実装**：フェーズごとに実装→動作確認→チェックを付ける。外部連携（API・認証など）は別のフェーズに分ける。途中で設計が変わったら、先にファイルを直してから進める
5. **完了**：
   - ファイル冒頭の状態を「完了」にする
   - 対象アプリの`CLAUDE.md`（開発の要点）と`README.md`（機能説明）には要点だけを1〜2行書き、詳しい経緯はこのファイルへのパスで示す（CLAUDE.mdに長い履歴を書かない）
   - コミット・pushはリポジトリごと（`app`と`app_data`）に確認してから行い、報告にはそれぞれの状態を書く
