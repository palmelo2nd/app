# 開発方針：漢字学習アプリ（Webフロントエンド版）

**Why:** 再起動時にも一貫した設計・実装を維持するための厳格ルール集。[[project-brain-dev-policy]]（Second Brain全体の方針）を漢字学習アプリ向けに具体化したもの。
**How to apply:** 新機能追加・バグ修正・リファクタリング時は必ずこのルールを参照すること。

---

## 1. ファイル構成・命名規則

| ファイル | 役割 |
|---|---|
| `index.html` | エントリポイント。DOM構造のみ。直接JSロジックは書かない |
| `css/style.css` | UIデザイン・レイアウト定義 |
| `js/app.js` | メイン制御（管制塔）。イベント監視・DOM操作に専念 |
| `js/modules/*.js` | 機能ロジック。1機能1ファイル |
| `data/kanjiMaster.json` | 漢字マスタ（後述）。コードリポジトリに同梱する静的アセット |
| （開発タブ） | **開発者専用機能**（`jukugo.json`の例文・対象級レビュー用）。本体アプリと同じ`index.html`/`js/app.js`内にナビゲーションタブとして統合されている（後述）。エンドユーザーには通常使わせない想定だが、配布物からは分離していない |

### 現在の modules 構成
`github.js`（リモート通信）／`storage.js`（LocalStorageキャッシュ。進捗トークン・キャッシュに加え、開発タブの未保存編集の永続化も担う）／`dataModel.js`（進捗データのMarkdownパース／文字列化、`kanjiMaster.json`・`jukugo.json`の列定義、学年⇔級の対応表）／`quiz.js`（読みクイズ・意味熟語クイズの出題ロジック）／`progress.js`（正答率集計・出題重み付け・苦手漢字抽出）／`devReview.js`（開発タブ：例文・対象級レビューのフィルタリング・編集差分マージ）

### modules の関数構成（必須4段落）
1. インポート（外部モジュール・ライブラリ）
2. インプット（引数でデータ・トークンを受け取る）
3. メイン機能（計算・データ加工・API通信）
4. アウトプット（`return` で結果を返す）

**禁止:** modules内でのDOM操作（`document.getElementById` 等）、OWNERやREPO名などの定数のハードコード（必ずインプットとして受け取る。定数自体は`js/app.js`側で管理する）。

## 2. データの分離方針（最重要・brainとの違い）

このアプリは「漢字マスタ（読み・意味・熟語）」と「学習進捗」を、**保存場所ごと完全に分離**する。brain（Second Brain）のmasterData/mainDataはどちらもユーザーが編集しうるため1つのdata.mdにまとめているが、漢字マスタはユーザーが編集しない固定の参照データなので、進捗と一緒くたにGitHubへ毎回PUTするのは無駄が大きく、方針を変えている。

| データ | 保存場所 | 性質 | 読み書き |
|---|---|---|---|
| 漢字マスタ（単漢字1対1の情報：`漢字`/`級`/`学年`/`画数`/`部首`/`部首名`/`音読み`/`訓読み`/`意味`/`送り仮名例`） | `code/kanzi/data/kanjiMaster.json`（**コードリポジトリ** `palmelo2nd/app`、ローカルの`code/kanzi`配下。GitHub上のリポジトリルート自体には`code/`は無く、`kanzi/data/kanjiMaster.json`が実際のリポジトリ内パス） | 固定。ユーザーは編集しない | 通常の`fetch('data/kanjiMaster.json')`で読み込むのみ。GitHub API・PAT不要 |
| 熟語マスタ（複数の漢字にまたがる情報：`種別`/`語`/`読み`/`意味`/`例文`/`使用漢字ID`/`対象級`/`構成`/`対象級_確認状態`/`熟字訓`/`類義語`/`対義語`/`出典`（`種別`='故事・諺'のみ）） | `code/kanzi/data/jukugo.json`（**コードリポジトリ**、同上。リポジトリ内パスは`kanzi/data/jukugo.json`） | 固定。ユーザーは編集しない | 通常時は同上（`fetch`のみ）。**例外**：開発タブ（4章参照）は、レビュー結果を保存する際にのみGitHub API（`CODE_OWNER`/`CODE_REPO`/`JUKUGO_REMOTE_PATH`＝`kanzi/data/jukugo.json`）でこのファイルへPUTする。`使用漢字ID`で`kanjiMaster.json`側の`ID`と紐付ける（2026-08-29、二字熟語〜四字熟語・故事諺を統合した単一の表として`kanjiMaster.json`から分離） |
| 学習進捗（`progressData`：出題回数・正解回数・連続正解・最終学習日時） | `data/kanzi/data.md`（**データリポジトリ** `palmelo2nd/app_data`、`kanzi/data.md`） | ユーザーごとに増減する | `github.js`＋`storage.js`経由。オフライン完全対応（後述） |

**漢字マスタ・熟語マスタを増補・修正する場合**（学年配当の追加・意味や熟語の追加など）は、`code/kanzi/data/kanjiMaster.json`・`data/jukugo.json`を直接編集し、コードリポジトリ側でコミットする（データリポジトリではない）。データ構造の設計根拠・全体像は[00_市場調査/出題範囲（公式基準）.md](./00_市場調査/出題範囲（公式基準）.md)・[01_技術調査/データ構造設計.md](./01_技術調査/データ構造設計.md)を参照。

## 3. 学習進捗データの通信ルール（最優先）

### オフライン完全対応
- 進捗の読み書きは `github.js`（リモート）と `storage.js`（LocalStorageキャッシュ）を必ず経由する。
- **読み込み:** GitHub API → 成功時はテキスト＋SHA をLocalStorageキャッシュ。失敗時はキャッシュから復元。
- **書き込み:** クイズ・フラッシュカードで1問回答するたびに、即座にLocalStorageへ反映する（`app.js`の`persistLocal`）。GitHubへのPUTは設定タブの「保存」ボタン押下時のみ行う（毎回API通信しない）。圏外・保存失敗時もデータはローカルに保持される。

### データパース・整合性
- `progressData`の行はIDをキーに`.find(r => r['ID'] === id)`でアクセスする。行番号・インデックス依存のアクセスは禁止。
- 出題対象は毎回`js/modules/quiz.js`の重み付け抽選（`progress.js`の`calcWeight`）で選ぶ。未学習・正答率が低い漢字ほど出やすい。

## 4. 実装の心得

- グローバル状態（`state`：現在のSHA・漢字マスタ・進捗配列・選択中の学年など）は `js/app.js` の`state`オブジェクトで一元管理する。
- DOM内テキストをデータソースとして直接扱うことは禁止。`state`を常に正とする。
- 外部ライブラリを追加する場合は`index.html`でCDN経由ロードし、JS側では`window.xxx`等グローバルオブジェクト経由で使う。modules内での個別インポート禁止（現状、外部ライブラリは未使用）。

  - **故事・諺クイズ（`buildJukugoTypeQuiz`にjukugoType='故事・諺'を渡して再利用、2026-09-01追加）**：準1級・1級専用。公式審査基準（「典拠のある四字熟語、故事成語・諺」）と対策サイトの実問題調査により、三字熟語・四字熟語と同じ「例文中のカタカナ部分を漢字に直す」形式と判明したため、画面・出題ロジックとも新規実装せず`buildJukugoTypeQuiz`をそのまま再利用した。ただし`故事・諺`の`語`は熟語全体ではなく`例文`（諺・成語の全文自体）中の空欄部分の断片（1〜4字）という点が他の`jukugoType`と異なるため、`buildJukugoTypeQuiz`に2点だけ分岐を追加した：①questionTextを「正しい${jukugoType}はどれ？」ではなく「正しい漢字はどれ？」にする（`語`が「故事・諺」そのものではなく断片のため）、②誤答候補を`語`と同じ文字数のエントリに限定する（他の`jukugoType`は`種別`自体が文字数を固定していたため元々問題にならなかったが、故事・諺は1〜4字が混在するため、文字数だけで正解が分かってしまうのを防ぐ）。データはウィクショナリー日本語版から収集した1,033件のうち、対象級を問わず重複・欠落の無い728件を導入（当初は対象語の漢字が準1級・1級に到達する340件のみを想定していたが、ユーザー方針「級が低くてもOK、準1級でも一部低級の出題がある」により対象級を問わず登録する方針に変更。導入時に元号混入43件を発見し除外。詳細は8章・[01_技術調査/故事諺データ調査.md](./01_技術調査/故事諺データ調査.md)参照）。**対象語の漢字が準1級・1級に届かない語は「故事・諺」タブ自体には出現しない**（`KYU_GENRE_MAP`で`kojiKotowaza`が準1級・1級にしか無いため）が、`jukugo.json`のデータとしては存在するため、対応する低い級の読みクイズ・書取クイズ等（`種別`を見ないジャンル）では通常どおり出題される。新設フィールド`出典`（`JUKUGO_COLUMNS`に追加）にウィクショナリーの`由来 ○○`カテゴリタグから取得した典拠を格納。Playwrightで準1級・1級双方のタブ表示・出題・正誤判定・次の問題遷移、既存ジャンル（四字熟語等）への影響が無いことを確認済み、コンソールエラー無し。
  - **誤字訂正クイズ（`buildGojiTeiseiQuiz`、2026-09-01追加）**：準1級・1級のみだった「故事・諺」と異なり5級以降が対象。公式の出題形式「文中の誤って使われている同じ読みの漢字を正しい漢字に直す」に合わせて実装したが、**専用の外部データが存在しない唯一のジャンル**（他ジャンルは何らかの一次情報源から出典・語彙を取得できたが、誤字訂正はWeb調査でも構造化データセットが見つからなかった。[01_技術調査/誤字訂正データ調査.md](./01_技術調査/誤字訂正データ調査.md)参照）だったため、既存データからの機械生成に踏み切った。生成方式：`kanjiMaster.json`の音読みが完全一致する別の漢字を、二字熟語の一方の文字に差し替える（IME変換ミスに近い性質を利用）。①差し替え結果が別の実在語にならないこと（`jukugo.json`の`語`一覧と照合）、②対象級が近い漢字であること（`KYU_ORDER`の差2段階以内）、③差し替え候補の読みが候補漢字にとって主要な読み（音読み配列のindex 1以下）であること、を必須条件とし、④[yi-bai/ids](https://github.com/yi-bai/ids)（MIT）のIDS（部品構成）データから「対象漢字を部品として含む／含まれる」＝視覚類似度`高`、「`kanjiMaster.json`の`部首`フィールドを除いた部品が共通」＝`中`、それ以外＝`低`、の3段階を判定し優先する。実例16問の分析（読み一致100%・視覚的類似50%）でこの設計の妥当性を検証済み。二字熟語7,097件中5,505件（78%、うち視覚類似度`高`または`中`が65%）に`誤字候補_文字`/`誤字候補_位置`/`誤字候補_読み`/`誤字候補_視覚類似度`/`誤字候補_確認状態`（`構成`/`構成_確信度`と同じフラットな構成、ネストしたオブジェクトにはしていない）を生成し`jukugo.json`へ追加（`js/modules/dataModel.js`の`JUKUGO_COLUMNS`にも追加）。クイズ自体は書取クイズに近い作り（`buildWritingQuiz`同様、`語`の一部を別の文字に置き換えた文を見せて正しい漢字を4択で選ばせる）で、誤答は`誤字候補_文字`自身と、スコープ内の同じ読みを持つ他の漢字（`kanjiList`から実行時に検索、IDSデータへの依存無し）から作る。CHISE本体（GPLv2）は組み込みを避け、MITライセンスの`yi-bai/ids`を採用した点に注意（05_リリース_ストア申請のクレジットTODOに追加要）。**開発タブ「誤字訂正レビュー」モード（2026-09-01追加、6章参照）で承認／保留／却下・内容修正ができる**。
- 「意味・熟語クイズ」「フラッシュカード」は公式の出題ジャンルではない独自機能のため、級タブの外に独立したnav項目として残している（読みクイズだけが「クイズ」タブの「漢字の読み」ジャンルへ吸収された）。

## 6. 開発タブ（例文・対象級・送り仮名・読み・書き・筆順・誤字訂正レビュー、開発者専用）

- **入り口**：2026-08-31以降、独立したnavボタンではなく**ヘッダーの`#kyu-select`（級プルダウン）の選択肢の1つ**（`value="dev"`）として統合されている（5章参照）。プルダウンで「開発」を選ぶと`switchView('dev')`が呼ばれて直接遷移し、他のnavボタン（ホーム等）で別画面へ移ると、プルダウンの表示は現在の対象級に戻る。
- **目的**：機械生成・大量投入した`jukugo.json`（例文・対象級）と`kanjiMaster.json`（送り仮名例・読み例・音読み訓読み・筆順）を、開発者がその場で承認／保留／却下し、内容を編集できるようにする（[01_技術調査/データ構造設計.md](./01_技術調査/データ構造設計.md)「データメンテナンス用UIの構想」の実装。第一弾＝熟語の例文・対象級、第二弾＝2026-08-31に漢字データの送り仮名・読み・書き・筆順、第三弾＝2026-09-01に熟語の構成・誤字訂正、第四弾＝2026-09-02に単漢字の読み例を追加）。
- **9モード構成**：「熟語データ」グループ（例文レビュー／対象級レビュー／熟語の構成レビュー／誤字訂正レビュー、`jukugo.json`が対象）と「漢字データ」グループ（送り仮名レビュー／読み例レビュー／読みレビュー／書きレビュー／筆順レビュー、`kanjiMaster.json`が対象）の2グループに分けてモードタブを表示する。
  - **熟語の構成レビュー（2026-09-01追加）**：`構成`データ投入プロジェクト（8章参照）で全二字熟語に付与した`構成`（ア〜オ）を対象に、`構成_確認状態`（`devReview.js`の`reviewFieldNames('kousei')`）で承認／保留／却下する。対象は二字熟語のみのため種別フィルタは表示せず、代わりに`構成_確信度`（'高'|'中'|'低'）で絞り込む専用の確信度フィルタを出す（`filterForReview`の`mode==='kousei'`分岐）。**低確信度（準1級・1級を中心に約450件）を優先的にレビューできるよう、確信度フィルタで「低」を選べば一覧できる**。行の内容編集は分類そのもの（ア〜オのセレクト）で、対象級レビューと同じく`contentField`を通して`state.dev.jukugoEdits`に反映される。
  - **誤字訂正レビュー（2026-09-01追加）**：`誤字候補_文字`を持つエントリ（5,505件）を対象に、`誤字候補_確認状態`（`reviewFieldNames('goji')`）で承認／保留／却下する。熟語の構成レビューと同じく種別フィルタは表示せず、代わりに`誤字候補_視覚類似度`（'高'|'中'|'低'）で絞り込む確信度フィルタを流用する（ラベルをJS側で「視覚類似度」に動的に差し替え、`updateDevFilterVisibility`参照）。行には`buildJukugoDevRow`の`mode==='goji'`分岐で「◯文字目「正字」を「誤字」に差し替え→誤字表記「××」（読み：○○）」というプレビュー行を追加表示し、内容編集は`誤字候補_文字`のテキスト入力（`example`モードと同じUIパターン）。**唯一、専用の外部データソースが無く機械生成のみに頼っているジャンルのため、他モードよりレビューの重要度が高い**（5章参照）。
  - **送り仮名レビュー**：`送り仮名例`は1字につき0〜数件の配列（`{語, 読み, 確認状態}`）を持つため、`devReview.js`の`flattenOkuriganaEntries`で1行=1例のフラットな一覧に展開してからレビューする。編集は`"漢字ID:配列index"`をキーにした`state.dev.okuriganaEdits`に記録し、`mergeOkuriganaReviewEdits`が該当する配列要素だけを差し替える。
  - **読み例レビュー（2026-09-02追加、同日「一覧」「チェック」の2サブタブに拡張）**：単漢字読みクイズ用の`読み例`（1字につき0〜数件の配列、`{語, 読み, 例文, 確認状態}`）を対象にレビューする。他の8モードと違い、モード内がさらに独立した2つのサブタブに分かれている（`#reading-example-subtabs`、`state.dev.readingExampleSubTab`）唯一のモード：
    - **「チェック」サブタブ**：従来どおり1件ずつのレビューリスト。送り仮名レビューと全く同じ枠組み（`flattenReadingExampleEntries`／`filterReadingExampleForReview`／`mergeReadingExampleReviewEdits`、キーは同じく`"漢字ID:配列index"`、`state.dev.readingExampleEdits`）でレビューする。行の見た目は他モードの平文リストと異なり、実際の読みクイズ（3章）と同じ`renderQuizSentence`で例文を描画して対象語をハイライト表示し、その直下に読みクイズの回答欄と同じ`kana-answer-input`クラスの入力欄を配置して正解の`読み`を初期値としてあらかじめ入れておく（`buildReadingExampleDevRow`）。開発者はこの「解答済みの問題」を見て内容の自然さ・正しさを判断するだけでよく、間違いに気づいた場合はその場で例文・読みを直接編集してから承認／保留／却下する。
    - **「一覧」サブタブ（デフォルト表示）**：対象級（`dev-filter-kyu`で選択、「すべて」ならヘッダーの対象級と同じ級）の配当漢字を**8列グリッド**（`renderReadingExampleOverview`、2026-09-02当初10列で実装したがはみ出しが生じたため8列に修正）で並べ、字ごとの読み例の承認状況を色分けする（未承認：赤／一部承認：黄／全部承認：緑、`readingExampleStatusOf`が両サブタブ・モーダルで共通のロジックを提供）。「なるべく多くの字を1ページで見渡せるように」というユーザー要望に基づき、通常のフィルタ・リスト・ページングは隠し（`updateReadingExampleSubtabVisibility`）、級の絞り込みだけ残す。**1字をクリックすると読み取り専用の漢字詳細モーダル**（`#kanji-detail-modal`、`openKanjiDetailModal`）が開き、漢字・音読み・訓読み・部首・部首名・画数・意味に加え、**その字を含み実際に出題されうる（＝例文を持つ）熟語を対象級を問わず全件**（`getMergedJukugoData`から`使用漢字ID`で検索、件数の多い字は最大87件確認済みだがモーダル内スクロールで対応）、読み例の一覧（例文＋正解＋確認状態バッジ、読み取り専用）を表示する。**モーダルの背景色も承認状況の3色に連動するが、承認ボタン自体はここには置いていない**（ユーザー方針：閲覧専用にし、実際の承認操作は「チェック」サブタブで行う）。
  - **読みレビュー／書きレビュー**：どちらも漢字1字単位で`読み_確認状態`／`書き_確認状態`を別々に持つ（同じ音読み・訓読みデータに対する2種類の独立したチェック）。「書き」は「読みの逆」＝読みを主役に表示し、対応する漢字が正しいかを確認する形式（`buildKanjiDevRow`が`mode==='writing'`で表示を反転）。
  - **筆順レビュー**：実データは`kanjiMaster.json`ではなく別ファイル`data/strokeOrder.json`（約15MB、[HanziWriter](https://hanziwriter.org/)形式`{strokes, medians}`、KanjiVG由来・CC-BY-SA 3.0、全5,514字中5,367字＝97%をカバー）にある。全ユーザーの初回読込を重くしないよう、開発タブで筆順モードを開いた瞬間だけ`ensureStrokeDataLoaded()`が`fetch`する（遅延読み込み、`state.strokeData`にキャッシュ）。表示はCDN経由でロードした`window.HanziWriter`（`index.html`で`<script>`タグ、`charDataLoader`で`strokeOrder.json`のデータをそのまま渡す）。確認状態は`筆順_確認状態`として`kanjiMaster.json`側に持つ（読み・書きと同じ`state.dev.kanjiEdits`を共有）。
- **編集の即時反映とローカル保持**：レビュー操作は即座に`state.dev.jukugoEdits`／`state.dev.kanjiEdits`／`state.dev.okuriganaEdits`／`state.dev.readingExampleEdits`（4種類に分離）に記録され、`storage.js`の対応する`save*ReviewEdits`でLocalStorageに永続化される（キーも4種類に分離）。ページを閉じても再読み込みしても失われない（進捗データの「オフライン完全対応」と同じ考え方）。
- **実効データ**：`getMergedJukugoData()`／`getMergedKanjiData()`がそれぞれfetch由来の元データに未保存編集を重ねた配列を返す。クイズの出題（`getScopedJukugoList()`・`getScopedKanjiList()`）もこちらを参照するため、GitHubへ保存する前でも編集内容をアプリ内ですぐ試せる。
- **GitHubへの保存**：「変更をGitHubに保存」ボタンで、`jukugo.json`と`kanjiMaster.json`のうち未保存編集がある方（両方の場合は両方）を独立してPUTする（`CODE_OWNER`/`CODE_REPO`固定、パスは`JUKUGO_REMOTE_PATH`／`KANJI_MASTER_REMOTE_PATH`）。保存直前に最新のリモート内容を取り直し、その上に編集を重ねてからPUTすることで他所での更新との競合を避ける（進捗保存の409ハンドリングと同じパターン）。一方が失敗してももう一方の結果には影響しない（失敗した方の編集はローカルに残る）。
- **認証**：設定タブと同じGitHub Personal Access Token（`state.token`）を使い回す。トークンには`palmelo2nd/app`（コードリポジトリ）への書き込み権限が必要（`palmelo2nd/app_data`とは別リポジトリ）。
- **モジュール分担**：フィルタリング・編集差分マージ等の純粋なデータ変換ロジックは`js/modules/devReview.js`に置く（4段落構成の例外なし、既存modulesと同じ規約に従う）。DOM操作・イベント処理・GitHub呼び出しの発火・HanziWriterの初期化は他タブと同様に`app.js`側で行う。
