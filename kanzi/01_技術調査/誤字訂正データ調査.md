# 「誤字訂正」ジャンルのデータ調査

確認日：2026-09-01。目的：漢検5級以降で出題される「誤字訂正」ジャンル（現状`data/jukugo.json`に対応データが無く「準備中」プレースホルダー）について、実際の出題例をWeb調査し、社内で試作した機械生成プロトタイプ（`kanjiMaster.json`の音読み・訓読みから「同じ読みの別漢字」への差し替え候補を生成する方式、7,097件の二字熟語中5,505件＝78%で対象級が近く実在語にならない候補を発見済み）の妥当性を検証する。**今回は調査のみで、コード・データの変更は行わない。**

## 2. 出題パターンの分析

### 「同じ読み」への差し替えは100%（16/16）

収集した全16問で、**誤字と正字は完全に同じ音読みを共有していた**（へき・かん・かい・かく・ち・しょう・しん・そう・せい・まん・れつ・ぼう・とう・と・ひ・はく）。訓読みの一致による誤字は今回のサンプルには出現しなかった（4級〜協会公式という範囲のため、より高い級では訓読みや熟字訓による誤りも出現する可能性はある）。**これは社内プロトタイプの核となる前提（読みが完全一致する漢字への差し替え）と完全に一致する**。

### 視覚的な近さは「あれば尚良い」が必須ではない（8/16が視覚的に類似）

当初の想定では「読みの一致」が主で「見た目の近さ」は副次的と考えていたが、実際には**16問中8問（50%）で、誤字と正字が同じ音符（フォネティック）を共有しており視覚的にも近い**（壁/璧、勧/歓、正/征、慢/漫、列/烈、冒/帽、被/疲、泊/拍）。特に正/征・列/烈・冒/帽の3問は、**正字が誤字をそのまま部分字形として含む**（例：「征」＝「彳」＋「正」）という、非常に紛らわしい関係になっている。残り8問（解/皆、格/較、致/置、紹/称、深/慎、燥/騒、透/盗、途/吐）は視覚的な類似が薄く、読みの一致のみが紛らわしさの根拠になっている。

→ **「読みの一致」は必須条件、「同じ音符を持つ（視覚的に近い）」は無ければ無いで成立するが、あれば紛らわしさの質が上がる加点要素**、という位置づけが実態に近い。

### 誤字の出現位置

16問中、1文字目が誤字＝7問（壁は熟語2文字目だが「双璧」の2文字目、勧・解・深・征・慢・列・冒・被・泊のうち先頭は勧・解・深・慢・冒・被・泊で7問、2文字目は壁・格・致・紹・燥・正・列・透・途で9問）。**明確な偏りは無く、熟語のどちらの文字も誤字になりうる**（社内プロトタイプの想定どおり）。

### 誤字として選ばれる漢字と正字の意味的関係

16問を見る限り、誤字はいずれも**正字とは意味的に無関係な、独立した実在の漢字**（例：「璧」の代わりに使われる「壁」は「かべ」という全く別の意味を持つ字で、字面や文脈上のつながりは無い）。誤字自体は常用漢字の範囲内の見慣れた字が使われる傾向があり（4級の問題という制約はあるが、壁・勧・解・格・致・紹・深・燥・正・慢・列・冒・透・途・被・泊はいずれも常用漢字）、**極端に難しい字・レアな字を誤字にはしない**。これは社内プロトタイプの「対象級が近い」という絞り込み方針を裏付ける。

### 生成された文が別の実在語にならないことの確認

16問全てで、誤字を含む熟語（双壁・勧迎会・解勤賞・比格・装致・紹号・深重・燥音・遠正・慢画・痛列・冒子・透作・途息・被労・泊手）は**いずれも実在しない語**だった（唯一紛らわしいのは「深重」で、これ単体では実在しないが「深」を含む別の実在語と誤認しないよう文脈が組まれている）。社内プロトタイプの「既存`jukugo.json`の`語`一覧と照合して実在語になる候補を除外する」というフィルタは、この点で妥当と言える。

## 4. 社内プロトタイプへの評価と改善提案

### 妥当性

- **「読みが完全一致する漢字への差し替え」という核となる生成ロジックは、実例16問全てと整合しており妥当**
- **「対象級が近い漢字を優先する」フィルタも、実例が概ね常用漢字の範囲内で構成されていることと整合し妥当**
- **「差し替え結果が実在語にならないことを確認する」フィルタも、実例が軒並み非実在語であることと整合し妥当**

### 改善提案：「同じ音符（フォネティック）を持つ漢字」を優先する重み付けを追加する

実例の50%（8/16）が、誤字と正字で音符（例：辟・雚・曼・皮・白等）を共有する、視覚的に酷似したペアだった。現在のプロトタイプ（読みが一致するかどうかのみで候補を選ぶ）では、この「見た目の近さ」を考慮できていない。以下の改善を提案する：

1. `kanjiMaster.json`に音符情報は無いため、まずは簡易的な近似として**部首を除いた残りの字形が一致するかどうか**（例：「征」から「彳」を除くと「正」、「烈」から「灬」を除くと「列」）を機械的に判定するロジックを検討する。ただし全ての字が「部首＋音符」のようなきれいな左右分割構造を持つわけではないため、100%の網羅は難しい
2. 完全一致が難しい場合の次善策として、**候補の中に「対象漢字を部分字形として含む、または対象漢字に部分字形として含まれる」ものがあれば優先的に採用する**という簡易ヒューリスティックが有効そうである（正/征、列/烈、冒/帽の3パターンはこの関係に該当）
3. 上記のような「視覚的に近い候補」が見つからない場合でも、読みが一致してさえいれば出題として成立する（解/皆、致/置等のパターン）ため、**視覚的な近さは必須条件にはせず、優先度を上げるボーナス条件として扱う**のが実例の実態に最も忠実

### その他の細かい留意点

- 誤字の位置（1文字目・2文字目）に偏りは無いため、プロトタイプ側で位置をランダムに選ぶ現在の設計のままで問題ない
- 対象級の近さについて、実例では誤字自体も常用漢字の範囲に収まっていたため、プロトタイプの「対象級の差が2段階以内」という基準は妥当だが、もう少し厳しく（1段階以内、またはむしろ同じか1つ下の級を優先）してもよいかもしれない（要検証）
- 今回の実例は4級中心で件数も16問と少ないため、**より上級（2級・準1級・1級）での傾向が同じかどうかは未検証**。上級では訓読みや熟字訓による誤りが増える可能性がある

## 5. 結論・次の一手

1. **誤字訂正専用の外部データセットは存在しない**ため、社内プロトタイプ（機械生成方式）をベースに進めるのが引き続き最善の方針
2. 実例調査により、核となる生成ロジック（同じ読みへの差し替え・対象級の近さ・非実在語化の確認）は**妥当性が裏付けられた**
3. 改善点として、**「対象漢字を部分字形として含む／含まれる」候補を優先するヒューリスティック**を追加することで、実例の質（50%が視覚的に酷似）に近づけられる見込み
4. 次の具体的な作業（未実施・提案のみ）：
   - 部分字形の包含関係を判定する簡易ロジック（文字列としての字形比較は難しいため、Unicode分解データベース（IDS：Ideographic Description Sequence）等の追加データソースが必要になる可能性がある。CHISE IDS等のオープンデータの調査が次のステップ
   - 改良したロジックで候補プールを再生成し、`真正`の量・質のバランスを確認
   - 生成した候補を対象級ごとにサンプリングし、実例と同じ基準（読み一致・対象級の近さ・非実在語化）で目視レビュー

## 6. IDS（部品構成）データの調査と改良版プロトタイプ（2026-09-01）

5章の提案に基づき、Unicode漢字の部品構成データ（IDS：Ideographic Description Sequence）の調査と、それを使った改良版プロトタイプの試作まで行った。

### データソース：yi-bai/ids（採用）

[yi-bai/ids](https://github.com/yi-bai/ids)（GitHub）を採用した。

| 項目 | 内容 |
|---|---|
| ライセンス | **MIT**（`Copyright (c) 2021 Yi Bai`、raw LICENSEファイルで確認済み） |
| データ形式 | `ids_lv1.txt`（102,031行）。1行＝「文字 TAB プライマリIDS[;代替IDS...]」。IDSはIDC演算子（⿰⿱⿴等）＋部品文字の列（例：`征	⿰彳正`＝「彳」と「正」の左右構成） |
| カバレッジ | `curl`で直接取得し`grep`で実在確認。**準1級・1級の激レア字（鼎・隗・蟷・螂・魑・魅・魍・魎等）も含め収録されていることを確認**（当初WebFetchツールでの間接確認では見つからなかったが、これはWebFetchが大きいファイルを要約処理する際に一部しか見ていなかったためと判明。直接`curl`＋`grep`で確認する方が確実） |
| CHISE由来かどうか | READMEに明記は無いが、他のIDSデータセット（CHISE本体はGPLv2）とは別に独自収集されたとみられる。少なくとも配布ライセンスはMITで問題なし |
| 比較検討したが不採用 | CHISE IDS本体（GPLv2、コピーレフトでありアプリへの組み込みに懸念）、`mandel59/kanji-database-ids`（同じくCHISE由来部分はGPLv2） |

### 部品共有の判定ロジック（試作・検証済み）

1. IDSから部品文字を抽出（IDC記号・カッコ内の異体字注記・PUA等を除去）
2. **「候補の部品リストに対象漢字自体が含まれる、またはその逆」＝`高`**（例：`征`＝⿰彳正 は`正`を部品として含む＝征/正ペアは`高`）
3. **`高`に該当しない場合、双方の部品リストから「自分自身の`部首`フィールドと一致する部品」を除いた上で、共通の部品が残るか＝`中`**（例：`壁`＝⿱辟土・`璧`＝⿱辟玉は、部首の`土`/`玉`を除くと共通部品`辟`が残る＝`中`）。**`kanjiMaster.json`の既存`部首`フィールドを流用するだけで、「意味的な部首（氵・扌・忄等）」と「音を担う部品（曼・白・皮等）」を機械的に区別できた**のが今回の発見
4. どちらにも該当しなければ`低`（読みの一致のみ）

1章で収集した実例11ペア（壁/璧・勧/歓・正/征・慢/漫・列/烈・冒/帽・被/疲・泊/拍）全てで、このロジックが実例と同じ`高`または`中`判定を再現できることを確認した。

### 改良版プロトタイプでの再生成結果

5章時点のプロトタイプ（読み一致＋対象級±2＋非実在語化のみ）に上記の部品共有判定を追加し、二字熟語7,097件全件で再実行した。

| 項目 | 件数 |
|---|---|
| 読みが2つの音読みにきれいに分解できた語 | 5,523件（78%） |
| そのうち候補が1件以上見つかった語 | 5,505件 |
| **そのうち`高`または`中`（視覚的にも紛らわしい）候補を持つ語** | **3,563件（withAnyCandidate中65%）** |
| `低`（読みの一致のみ）候補しか無かった語 | 1,942件 |

実例調査（1章）で「16問中8問＝50%が視覚的に酷似」だった結果と近い比率（65%）が機械的に再現できた。生成例：「帽子」→冒（実例の「冒子」の誤りと完全一致）、「少女」→小（少/小は日本語学習者が実際によく混同する組み合わせとして知られる）、「花壇」→化、「人口」→高、等。

### 残課題

- 一部の読み対応（例：「灯火」→丁、「九月」→究）で、`kanjiMaster.json`側の音読みデータの粒度・精度に起因すると見られる不自然な組み合わせが混じっている可能性があり、実装時にはランダムサンプルでの目視レビューが必要
- `ids_lv1.txt`は変異体（異体字・字体差）を複数候補として持つ字もあり、今回は先頭（プライマリ）のIDSのみを使用した。まれに実態と異なる分解になっている可能性は排除できていない
- 訓読みでの誤字（実例には出現しなかったが上級で増える可能性、5章参照）には今回のロジックは未対応（音読みのみを対象にした）

## 8. 本実装の結果（2026-09-01）

ユーザーから「実装お願いします」との指示を受け、6章の改良版プロトタイプをベースに本番データ投入とクイズ実装を行った。

- **追加の品質改善**：候補漢字にとって共有した読みが「主要な読みかどうか」（`kanjiMaster.json`の音読み配列でのインデックス、0=最も一般的）を優先条件に追加した。従来ロジックでは「灯火」の差し替え候補として`丁`（`とう`は`丁`の4番目の音読み＝かなり obscure）が選ばれていたが、この改善により`刀`（`とう`が1番目）が選ばれるようになった。最終的に5,505件中5,503件（99.96%）が候補漢字にとって1〜2番目に一般的な読みでの差し替えとなった
- **データ投入**：二字熟語7,097件中5,505件（78%）に`誤字訂正候補`（`{位置, 誤字, 読み, 視覚類似度, 確認状態}`）を生成し、既存の`data/jukugo.json`の各エントリに新規フィールドとして追加した（新しい`種別`は作らず既存の二字熟語エントリを拡張する形。`js/modules/dataModel.js`の`JUKUGO_COLUMNS`にも追加）。視覚類似度の内訳は`高`1,673・`中`1,829・`低`2,003
- **クイズ実装**：`js/modules/quiz.js`に`buildGojiTeiseiQuiz`を新規実装。書取クイズに近い作りで、対象語の1文字を`誤字`に差し替えた文を見せ、正しい漢字を4択で選ばせる。誤答は`誤字`自身と、出題範囲内で正解と同じ読みを持つ他の漢字（`kanjiList`から実行時に検索、IDSデータへの依存は無し）から作る
- **動作確認**：Playwrightで5級・3級・準1級・1級での出題・正誤判定・次の問題遷移、10回連続の出題サイクルでのクラッシュ無し、既存ジャンル（読みクイズ等）への回帰無しを確認。コンソールエラー無し
- **開発タブレビューUI**：2026-09-01に追加実装した。データ構造を`誤字訂正候補`（ネストオブジェクト）から`誤字候補_文字`／`誤字候補_位置`／`誤字候補_読み`／`誤字候補_視覚類似度`／`誤字候補_確認状態`という`構成`/`構成_確信度`と同じフラットな構成へリファクタリングしたことで、既存の「熟語の構成レビュー」と同じパターンをそのまま踏襲でき、新規実装は最小限で済んだ（CLAUDE.md 6章・開発履歴参照）。`確認状態`は導入時点でまだ5,505件全てが`未確認`のままで、実際のレビュー作業自体は今後の課題
