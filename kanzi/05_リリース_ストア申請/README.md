# リリース・ストア申請

App Store／Google Playへの申請・掲載に関する記録フォルダ。

## 【2026-09-03決定】初回リリースのスコープ（MVP）

ユーザー判断により、以下の方針で初回リリースを進める（[02_デザイン/UX設計.md](../02_デザイン/UX設計.md#2026-09-03決定初回リリースはiosandroidストアへ直接全級無料ローカル保存のみ)に詳細）。

- **配信先**：iOS/Android両ストアへ直接申請（Web版を経由しない）
- **対象級（2026-09-03、さらに絞り込み）**：**初回は10級・9級・8級の3級のみ**を公開する。この3級で出題される公式ジャンルは「漢字の読み」「漢字の書取」「筆順・画数」「部首・部首名」「送り仮名」「対義語」「同じ漢字の読み」の7ジャンル（[00_市場調査/出題範囲（公式基準）.md](../00_市場調査/出題範囲（公式基準）.md)参照）で、いずれも実装・データとも完成済み（[README.md](../README.md)参照）。**7級〜1級は今回のリリースには含めず、リリース後のアップデートで順次追加する**（8ジャンルの実装自体は既に完成済みのため、追加時の作業は主に級の解禁・QA・ストア更新申請になる想定）
- **価格**：上記10〜8級の範囲を無料公開。段階的アンロック（課金）は次回以降のアップデートで検討
- **進捗保存**：LocalStorageのみ（GitHub PAT経由のクラウド同期は行わない）。機種変更時に進捗が引き継げない制約は初回リリースでは許容する
- **配布物から除外するもの**：「設定」タブのGitHub PAT入力欄、「開発」タブ（開発者専用機能一式）。いずれも一般ユーザー・ストア審査向けには不要かつ不適切なため、ストア提出ビルドからは取り除く（実装方法は[01_技術調査](../01_技術調査/README.md)のCapacitor移行作業と合わせて検討）

## 【2026-09-06決定・上記を改訂】初回リリース対象をさらに10級・9級の2級のみへ絞り込み

「まずは小スケールの機能でアプリ実装・ストア申請の流れそのものを一度試してみる」ことを優先し、**上記2026-09-03決定の「10級・9級・8級の3級」から、対象をさらに10級・9級の2級のみへ絞り込む**方針にユーザーが決定した（[初回トライアルリリース_タスクリスト.md](./初回トライアルリリース_タスクリスト.md)参照）。

- **対象ジャンル**：10級・9級で出題される「漢字の読み」「漢字の書取」「筆順・画数」の3ジャンル（[00_市場調査/出題範囲（公式基準）.md](../00_市場調査/出題範囲（公式基準）.md)参照）。8級以降にしか出ない「部首・部首名」「送り仮名」「対義語」「同じ漢字の読み」は今回のスコープからいったん外れる
- **理由**：本番同等の申請・審査プロセスを一度小さく経験し、勝手が分かった上で8級以降・他ジャンルへ拡張していく方が手戻りが少ないというユーザー判断。8級を含む3級構成は「トライアル後の本来のMVP」として維持し、リリース後のアップデートで解禁する想定（[初回トライアルリリース_タスクリスト.md](./初回トライアルリリース_タスクリスト.md)「位置づけ」参照）
- **影響する既存記録**：[00_市場調査/収益予測.md](../00_市場調査/収益予測.md)の「初回リリースは10級・9級・8級のみ無料公開」の記載は本決定により対象級が変わったため、参照時は本項を優先すること（当該ファイル側にも追記予定）

## 【2026-09-06決定】プライバシーポリシーの公開方法

ストア審査に必須の「プライバシーポリシー公開URL」（下記「審査を通すための条件」参照）の公開先を検討し、**既存のブログ運営用レンタルサーバーに1ページ追加する形（案B）**で公開する方針に決定した。

- **検討した選択肢**：
  - 案A：GitHub Pagesでプライバシーポリシー専用の空リポジトリを新規作成して公開（技術的にはコード流出リスクはゼロと確認済み。非公開リポジトリは公開リポジトリの一覧にも検索にも出てこないため）
  - 案B：既存のブログ運営用レンタルサーバーに1ページ追加して公開（**採用**）
  - 案C：配偶者のGitHubアカウントを借りて公開（非推奨として却下。案Aで同じ懸念が解消できる上、長期保守でアクセス権の所在が曖昧になるデメリットが大きい）
- **理由**：案Aは技術的にコード流出の心配は無いと確認できたが、GitHubのユーザー名が公開URLに残ること自体を避けたいというユーザーの判断により、GitHubを一切経由しない案Bを選択した。既に運用中の自分のドメイン・サーバーを使うため、身元やコードとの紐付けを自分で完全にコントロールできる
- **既存ブログ運営への影響（2026-09-06時点の想定、要実地確認）**：プライバシーポリシーは数KB程度の静的テキストページのため、容量・通信量ともブログ記事1本以下の負荷。新規URLパスを1つ追加するだけで既存記事・デザイン・SEOには触れない想定。CMSで「固定ページ」を作りメニューに載せなければ見た目上の変化もない想定

## 審査を通すための条件（2026-09-06調査）

### 両ストア共通
- **プライバシーポリシーの公開URLが必須**（データ収集の有無を問わず、無料・有料アプリいずれも）。MVPはLocalStorageのみで外部送信・アカウントなしのため内容はシンプルにできるが、公開URL自体は用意する必要がある（公開先は既存のブログ用レンタルサーバーに決定済み。上記「【2026-09-06決定】プライバシーポリシーの公開方法」参照）
- アプリが実際に動作すること（クラッシュ・プレースホルダーテキスト・壊れたリンクがあると却下対象）
- ストア掲載情報一式が必要：アプリ名・説明文・スクリーンショット（対応画面サイズぶん）・アイコン・カテゴリ・対応言語・問い合わせ先
- 年齢レーティング／コンテンツレーティングの申告（Appleは質問票への回答、Googleは無料のIARC質問票）

### Apple App Store固有
- **App Privacyラベル（プライバシー「栄養成分表示」）**：App Store Connect上でデータ収集項目を申告する。実際のアプリの挙動と食い違うと却下・アカウント停止のリスクがある（例：「収集なし」と申告しながら裏で解析SDKが動いている等）。**MVPはPAT入力・解析ツールとも無しのため「収集データなし」で申告しやすい**
- 輸出コンプライアンス（暗号化）申告：HTTPS通信のみであれば通常は標準の例外規定に該当し追加書類は不要なことが多いが、申告自体は毎回必須
- **Kids Category（子供向けカテゴリ）への登録は任意で、本アプリは非対象でよいと考えられる**：漢検10級〜1級（大人向けの内容も含む）を将来的に扱う想定で対象年齢が小学生に限定されないため、通常の「教育」カテゴリで問題ない。Kids Categoryに入れる場合は①第三者への個人情報・端末情報送信の禁止、②広告を入れるなら人手レビュー済みの年齢適合広告のみ、③外部リンク・課金には保護者ゲート必須、という厳格な追加ルールが課される（MVPには該当機能が無いため現時点では影響しない）
- Guideline 4.2（最低限の機能性）：内容が薄いテンプレート的アプリは却下されやすいとされる。実際の学習コンテンツ（クイズ・フラッシュカード）を伴うため該当リスクは低いと考えられるが、**トライアル対象の10級・9級（2級・3ジャンルのみ、2026-09-06決定）のボリュームで十分と判断されるかは提出してみないと分からない**（該当リスクが高いと分かった場合は8級以降を先に追加してから提出する判断もありうる）

### Google Play固有
- **データセーフティフォーム**：収集データの種類・用途をPlay Console上で申告する。Appleと同様、実態との不一致が却下・アカウント停止の理由になりうる
- **対象年齢層（Target audience）とファミリーポリシー**：「13歳未満を対象に含む」と申告すると、Google Play Families Policyの対象になり、広告SDKを認定済みのものに限定・パーソナライズ広告禁止・年齢確認画面の設置等、厳格な追加ルールが課される。**本アプリは小学生〜大人まで対象に含む想定のため、対象年齢層の申告内容（「13歳以上のみ」と申告できるか）を慎重に検討する必要がある**（要確認事項として上記TODOに追加）
- **新規デベロッパーアカウントの「12人×14日間クローズドテスト」必須化**：2023年11月13日以降に作成した個人アカウントは、本番リリース申請の前に12人以上のテスターに14日間連続で参加してもらう必要がある（法人アカウントとして登録すれば免除）。**個人アカウントで登録する場合、テスター12人の確保とスケジュールを見込んでおく必要がある**
- 2026年9月以降、Google Playは開発者の本人確認プロセスをさらに強化する予定（詳細は今後の公式アナウンス待ち、要継続確認）
